# Verilog 代码风格检查

检查最终 RTL 是否遵守[代码风格规范](rtl-coding-standard.md)第 1～8 节。机器检查确定的
规则，AI 补查机器未覆盖的适用规则。文内片段和第 9 节完整模块用于参考写法，示例的具体
电路不作为其他模块的要求。检查范围是代码风格，协议、流水、资源和 IP 选型由设计确定。

## 检查范围

- 新模块：检查完整实现。
- 已有模块：检查本轮改动及受影响的逻辑。声明变更需查看其使用处，状态、复位、握手和
  流水变更需沿相关控制与数据关系展开，不能只读差异行。
- 缺少可靠修改前文本、大范围重写，或预处理等使机器结构检查不完整时，扩大至完整文件
  及相应依赖。请求中的差异只是定位线索，不是完整影响分析。

机器仍快速扫描变更文件及已解析的 include 文件，不隐藏确定的违规。AI 根据机器报告补查
其未覆盖的编码规则，例如缩进和表达式排版、声明类型与驱动方式、组合赋值完整性、
FSM 职责分区、位宽与符号的明确表达、参数边界和函数写法。规则以规范正文为准，
不另建一套检查规范；同一版本已读规则可复用，只查必要的示例段落。

hook 复用编码前基线，保留同一模块中方向未变的原端口名；新增或改名端口仍按规范检查。

发现违规后修正并复检。修复会改变接口、周期或电路行为时，先说明冲突和影响，按任务授权
处理，不能为清除告警擅自改变既定设计。功能验证、时序分析和设计优化沿用各自流程。

## 编码结束时自动执行

`scripts/rtl_check_hook.py` 在 `UserPromptSubmit` 保存手写源码基线，在 `Stop` 检查新增或
修改的文件。无改动时安静返回；没有对应最终源码的 AI 检查结果时，自动要求当前 AI 继续：

1. 读取 `review-request.json` 的文件、审查范围和机器报告，按上述范围补查规范。
2. 修复违规；源码改变后用请求内的 `refresh_hook_argv` 和 `refresh_hook_input` 刷新请求。
3. 检查最终版本，将 `result_template` 保存为请求指定的 `review-result.json`。
   每个文件确认 `reviewed: true`，`findings` 只保留尚未修复的违规或无法判断项；
   无问题时为空。每个发现写规则出处、源码行号和原因，状态为 `fail` 或 `unresolved`。
4. 正常结束，由 hook 自动复检。

不逐章填写通过理由，也不为未使用的专题写不适用说明。未检查的文件保持 `reviewed: false`；
未决项不能省略或写成通过。记录只确认本轮检查完成，不证明 AI 判断正确。

hook 绑定最终源码、实际 include 依赖、规范文件的版本及审查范围；变更后旧记录失效。
机器明确违规、解析失败或缺少依赖不能用 AI 结果覆盖。只有机器明确标记为可补查的覆盖
缺口，完成相应结构及依赖审查后才可记为 `reviewed_with_limits`，仍保留机器未完成的限制。
宏、include 和条件编译的覆盖缺口需查看受影响的源码分支，不能只审当前启用的一支。

每用户轮次最多自动续做一次；仍未完成时告知问题并保留待检查文件。临时状态保存在系统
临时目录 `fpga-cowork-rtl-hooks`，不写入工程文档，不修改 RTL，也不启动 Vivado。

## 机器检查覆盖

`scripts/check_rtl.py` 使用词法扫描与 pyslang 语法树。下表是工具实际覆盖，未列出的规则
仍需在本轮审查范围内由 AI 判断；已经由机器可靠检查的项目不重复写合规证明。

| 编号 | 实际检查 | 来源 |
|---|---|---|
| FMT-002～005 | 无 Tab、无行尾空白、末尾换行、每行不超过 100 字符 | §2 |
| FILE-001 | 同名单模块、小写下划线文件名 | §1～2 |
| PARSE-001 | 源码解析；失败或缺少解析依赖标为未完成 | 解析前提 |
| PORT-001 | ANSI 端口、显式方向与 wire/reg 类型、方向后缀及固定时钟复位命名 | §1～2 |
| NAME-001 | 参数、函数、实例、generate 块命名及过程赋值量的 `_reg/_wire` 后缀 | §1 |
| INST-001、SYN-001 | 命名端口连接、命名参数覆盖、禁用 defparam | §2 |
| PROC-001～002 | 时序非阻塞、组合阻塞、`always @(*)`；按 `clk`/`rst` 名称字段区分边沿信号，角色不明时交 AI 核对 | §3～4 |
| BLOCK-001、CASE-001 | 分支和循环体 begin/end、case default、禁用 casex | §3 |
| DRIVER-001 | 多个 always/assign 驱动；generate 互斥或阵列写入范围不明时标未完成 | §1 |
| FSM-001～002 | `state_reg/next_state_wire` 分区、默认保持、定宽状态常量及状态译码写法 | §6 |
| DECL-001～002 | 同一声明的多个信号、wire 声明时赋值 | §1 |
| SYN-002 | 定位 full_case/parallel_case；是否代替完整赋值需 AI 判断 | §3 |

检查器读取 UTF-8 源码，不能读取时报告输入错误及未完成。区分注释、字符串和语法，
循环控制赋值按语言语法处理。解析采用 pyslang 的 Verilog-2005 模式，不证明完整
Verilog-2001 合规，不执行参数展开或综合。
`.vh` 仅查片段格式和直接词法规则，其结构需结合使用处审查。宏、include 和条件编译
影响结构解析时明确报告限制；不把格式检查通过当作完整规范、功能或时序通过。

## 配置与依赖

技能目录本身不注册 hook。目标工程 `.codex/hooks.json` 的 `UserPromptSubmit` 和 `Stop`
使用同一同步 `command`，超时 30 秒，保留已有 hook：

```text
<Python绝对路径> "<技能目录>/scripts/rtl_check_hook.py" --include "<手写RTL目录>"
```

`--include` 可重复，使用工程内相对目录，如 `common/rtl`，排除测试、厂商及生成目录。
范围内 `.v/.vh/.sv/.svh` 都跟踪；机器只接受 `.v/.vh`，其他扩展名报告未完成，不能绕过
生产 RTL 的语言要求。忽略链接及常见生成目录。include 仅解析工程内相对字面量路径；
依赖缺失、越界、链接或宏文件名保持未完成。并行任务对扫描范围内的变化也会被检查。

一次性使用 hook 的 Python 安装匹配依赖，运行 hook 时不联网安装：

```text
"<Python绝对路径>" -m pip install --target "<依赖目录>" pyslang==12.0.0 nanobind-backend==1.0.0
```

Windows 默认依赖目录为 `%LOCALAPPDATA%/fpga-cowork/python-deps/pyslang-12.0.0`，
也可用 `FPGA_COWORK_PYSLANG_PATH` 指定；缺失或版本不符报告未完成。
按 [Codex Hooks 说明](https://learn.chatgpt.com/docs/hooks)，非托管 hook 需信任；配置存在
不等于启用。在支持的 Codex CLI 中通过 `/hooks` 审阅并信任，再核对启用状态及实际运行。

## 手动检查与维护

未启用 hook、自动范围外文件或只读审查，显式运行机器检查，再按本文范围补查未覆盖规则：

```text
python "<技能目录>/scripts/check_rtl.py" --format json "<模块绝对路径.v>" "<头文件绝对路径.vh>"
```

手动检查既有模块时，可对单个模块加 `--baseline "<修改前源码路径>"`，用于保留原端口名。

机器退出码：0 为已覆盖项目通过，1 为违规，2 为输入错误或未完成；违规与未完成同时存在
时返回 2。向用户只报告实际问题、未决项和检查范围，无需输出逐条合规清单。

误报应修正检查器，不靠整文件忽略或伪填通过消除。维护检查器后运行行为测试：

```text
python "<技能目录>/scripts/test_check_rtl.py"
python "<技能目录>/scripts/test_rtl_structure.py"
python "<技能目录>/scripts/test_rtl_check_hook.py"
```
